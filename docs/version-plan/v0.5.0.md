# v0.5.0

## 版本性质
主版本。

## 版本定位
这是“内部协议和工具执行体系长成型”的版本。

## 本版目标
同时完成三项核心升级：
- Provider 适配层；
- 工具编排层；
- 文件历史与结构化工具结果。

## 为什么这一版必须做
前面产品已经可用，但内部还存在三个风险：
- provider 差异可能泄露到业务层；
- 工具执行仍容易分散在多个地方；
- 写入类工具缺少统一历史与结果模型。

如果不做这一步，后面接 MCP、Skills、后台会话时会越来越难维护。

## 本版要做什么
### 1. 建立 provider adapter 层
新增：
- `src/llm/adapter.ts`
- `src/llm/contracts.ts`
- `src/llm/providers/qwen.ts`
- `src/llm/providers/zhipu.ts`
- `src/llm/providers/deepseek.ts`

目标：
- 上层不再直接解析厂商原始响应；
- streaming 也通过统一内部事件输出；
- 错误模型统一。

### 2. 建立工具编排层
新增：
- `src/tools/orchestrator.ts`
- `src/tools/executor.ts`
- `src/tools/events.ts`

目标：
- QueryLoop 不再直接调用某个具体工具；
- 所有工具都走统一 orchestrator；
- 权限、进度、结果、历史都通过统一执行链路处理。

### 3. 建立文件历史与快照
新增：
- `src/tools/history.ts`
- `src/tools/fileSnapshot.ts`

目标：
- 写入前记录旧内容；
- 为回滚、diff、审查预留基础；
- 不依赖 git 也有最小历史记录。

### 4. 统一工具结果模型
建议统一：
- `status`
- `summary`
- `payload`
- `artifacts`
- `suggestedNextStep`

## 本版结束后的产品状态
- 产品内部第一次具备“平台感”；
- provider 与工具系统都开始有稳定边界；

## 是否已可用
- 对你自己：是，而且更稳。
- 对小范围试用者：可以。
- 对更广泛用户：还需要工程化收口。

## 本版主要学习目标
- 理解统一内部协议为什么比“多写几个兼容分支”更重要；
- 理解工具执行器为什么是工具系统成熟的标志；
- 学会给写入类工具补历史与结构化结果。

## 本版能学到的技术点
- 如何用 Adapter Pattern 隔离不同模型厂商的消息格式、流式协议和错误模型；
- 如何设计工具编排层，把权限、执行、进度、历史、结果统一收口；
- 如何定义结构化 Tool Result，避免不同工具各说各话；
- 如何为写入类工具建立最小文件快照和历史记录能力；
- 如何通过统一内部协议降低后续接 MCP、Skills、后台会话时的复杂度。

## 本版不要做什么
- 不做分包工程；
- 不做 MCP / Skills；
- 不做后台守护进程；
- 不做子 Agent；
- 不做长会话压缩系统。
