# v0.2.0

## 版本定位
这是“多 provider 真正长成一层适配系统”的版本。

前面虽然已经支持不同 provider，但本质上仍偏向“配置切换”。这一版要开始学习参考项目的精华之一：统一内部协议，屏蔽外部差异。

## 本版目标
建立 provider adapter 层，实现：
- 统一消息输入协议；
- 统一工具调用结果协议；
- 统一流式事件协议；
- 不同 provider 差异都收敛在适配层内。

## 对齐参考仓库的重点
重点参考：
- `claude-code-fork/docs/plans/openai-compatibility.md`
- `claude-code-fork/src/services/api/openai/index.ts`
- `claude-code-fork/src/services/api/openai/streamAdapter.ts`

本版主要学“内部统一协议”而不是“到处写 if provider === xxx”。

## 本版要做什么
### 1. 定义内部 provider 协议
新建：
- `src/llm/types.ts`
- `src/llm/adapter.ts`
- `src/llm/contracts.ts`

建议统一抽象：
- `ProviderRequest`
- `ProviderResponse`
- `ProviderStreamEvent`
- `ProviderToolCall`
- `ProviderToolResult`

### 2. 将不同厂商实现拆进单独目录
建议新增：
- `src/llm/providers/qwen.ts`
- `src/llm/providers/zhipu.ts`
- `src/llm/providers/deepseek.ts`

每个 provider 只负责：
- URL / Header / 参数适配；
- 将厂商返回结构翻译成内部协议；
- 将流式事件翻译成统一事件。

### 3. QueryEngine / QueryLoop 只依赖内部协议
从这一版开始，业务层不能再关心：
- 哪家 provider 的字段名是什么；
- tool call 是什么格式；
- 流式数据如何切片。

### 4. 完善 provider 级错误模型
建议统一：
- `rate_limit`
- `timeout`
- `network`
- `auth`
- `invalid_request`
- `server_error`

## 建议目录形态
```text
src/
├─ llm/
│  ├─ adapter.ts
│  ├─ contracts.ts
│  ├─ types.ts
│  ├─ stream.ts
│  └─ providers/
│     ├─ qwen.ts
│     ├─ zhipu.ts
│     └─ deepseek.ts
├─ core/
│  └─ errors.ts
└─ app/
   └─ queryEngine.ts
```

## 关键代码任务
- 现有 `chatClient.ts` 需要拆成“公共传输逻辑 + provider 适配实现”；
- `queryLoop` 不允许直接解析厂商原始响应；
- streaming 场景下，provider 层必须输出统一事件；
- 错误分类要统一，方便 doctor、REPL、日志复用。

## 本版结束后的产品状态
- 产品具备真正的 provider adapter 层；
- 换模型提供商不再影响上层循环、会话、工具逻辑；
- 项目内部结构第一次接近参考项目“通信层隔离”的思路。

## 本版主要学习目标
- 理解适配器模式在 AI 产品里的价值；
- 理解“统一内部协议”为什么是复杂系统的关键支点；
- 学会把“外部复杂性”关进一层边界内。

## 本版不要做什么
- 不做自动 provider 降级；
- 不做复杂负载均衡；
- 不做账号池；
- 不做多模型协同；
- 不做远程代理服务。
